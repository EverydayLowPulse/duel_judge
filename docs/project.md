# デュエマ裁定確認AIエージェント

## 基本的な挙動

ユーザーが投げた質問について次のように処理を行う。

1. 質問を読む
2. 質問内で挙げられたカードの能力について調査する。略称が用いられている場合、まずローカルの略称辞書を引き、なければ公式カード検索（必要ならweb検索）により正式名称を特定する。正式名称が特定できたら、公式DBから能力テキストを取得する。あわせて公式Q&Aをカード名で検索する。特定できなかった場合、ユーザーに確認する
3. 質問内容について、公式ルールとQ＆Aを参照し回答する。回答の際は論拠と出典を示す。

### 公式DBの取得方法（調査済み）

独立したJSON APIはない。ただしヘッドレスブラウザは不要で、通常のHTTPだけで取得できる。

| 操作 | 方法 |
|------|------|
| カード検索 | `POST https://dm.takaratomy.co.jp/card/`（フォーム送信）。応答はHTML断片 |
| カード詳細 | `GET https://dm.takaratomy.co.jp/card/detail/?id={card_id}`。能力テキストを含む |
| Q&A検索 | `POST https://dm.takaratomy.co.jp/rule/qa/`（`qa_w` 等）。記事一覧が返る |
| Q&A記事 | `GET https://dm.takaratomy.co.jp/rule/qa/{id}/`。本文に `Q` / `A` がある |
| 総合ルール | PDF。例: `https://dm.takaratomy.co.jp/img/dm_rule_20260410_4.pdf`（Ver.1.50, 2026/04/10） |

補足:

- URLの `?v={JSON}` はブラウザ履歴用。GETだけでは検索条件が効かない（全件一覧になる）。検索はPOST必須
- 検索結果一覧には**カード名がなく、`id` とサムネイルだけ**。名前・能力を知るには詳細ページを取る必要がある
- キーワード検索は部分一致寄りの挙動。「レッドゾーン」で関連カードが多数ヒットする。正式名確定後は詳細ページのタイトルで突合する
- `samename=on` は同一カードの再録を増やす。MVPではオフ想定。キャッシュキーは印刷物IDではなく**カード正式名**単位がよい
- 詳細ページに「このカードのよくある質問」への専用リンクは確認できなかった。カード関連Q&Aは公式Q&A検索（`qa_w=カード名`）で取る
- Q&A一覧はページネーションあり（少なくとも `/rule/qa/page/396/` まで）。旧Q&Aは `/rule/qa_old/` も存在
- 総合ルールはPDF。ルール番号（例: `111.` / `000.1.`）が付いているので、索引v1のメタデータ抽出は現実的

## 処理フロー

```
質問 → カード名解決 → （曖昧なら確認して待機）→ 公式DBから能力取得
                                                          ↓
回答＋引用 ← 出典検証 ← 裁定推論 ← 候補統合・再順位付け
                              ↑
         決定的validators + 残余LLM検証（宣言条件・前提差分）
                                          ↑
                         複数のルール/Q&A検索 ← RuleConcept注入
                                          ↑
                  論点分類（issues）← ScenarioFacts（構造化事実）
                                          ↑
                  検索プラン（固有名→イベント→汎用概念）
                ↓（不十分な場合）
         修復生成1回 or 回答保留（withhold）
```

段階ごとにツールを呼び出すエージェント構成とする（1回のプロンプトにすべて詰め込まない）。

現状の推論は **ゲーム進行のフルシミュレーションではなく、論点駆動＋原則制約＋LLM** である。  
ターンプレイヤー順でのステップ追跡は将来の別ブランチ実験候補（詳細は `docs/inference_approaches.md`）。

- `resolve_card_name()` — カード名解決（後述）
- `fetch_card_from_official_db()` — 公式DBからカード能力を取得（検索POST→id特定→詳細GET）。ローカルキャッシュを先に確認し、ミスまたはTTL切れの場合のみ公式へ取得しに行く
- `plan_search()` — 質問を固有名・イベント・汎用ルール概念に構造化し、Q&A用と総合ルール用の短い検索語を複数生成する。LLMの出力は検索補助にだけ使い、回答根拠にはしない
- `resolve_scenario_cards()` — 質問中の複数カードを公式DBで解決し、カード種類・文明・パワー・コスト・種族・能力テキストを取得する。名前一致しない近似候補は採用しない
- `build_scenario_facts()` — 質問で主張された事実を `ScenarioFacts` に落とす。カード属性は公式DBで上書きし、LLM推測は validator に渡さない
- `classify_issues()` — 論点分類（マナ支払い・視点・待機能力など）。`RuleConcept` 解決と決定的 validator 起動の入口
- `search_rules_and_qa()` — 検索プランの複数クエリを実行し、重複を統合・再順位付けする。公式Q&Aは `qa_w`、総合ルールはローカル索引を使う。ontology の `ruleRefs` / `qaSeeds` を強制注入する
- `run_validators()` — 汎用ルールを純関数で判定（例: 多色マナ支払い）。`not_allowed` のときは LLM を介さず総合ルール引用付き回答を組み立て、Evidence Gate へ渡す
- `verify_declaration_preconditions()` — 使用宣言時点のクリーチャーを固定し、各能力の文明・種族・コスト・パワー条件を公式カード情報と照合する。後の進化や効果解決で条件を満たしても、宣言時点へ遡って許可しない（決定的に解けない残余をLLMが担当）
- `generate_answer()` — 論拠付き回答の生成（内部はJSON。詳細は `docs/answer_format.md`）

最終段階で **Evidence Gate（出典ゲート）** を設ける。

- 引用がなければ回答を出さない
- 引用URLの実在を検証する
- URLの実在だけでは「実在するページに存在しない裁定を紐付ける」ハルシネーションを防げないため、引用文言がそのページ（取得済みテキスト）に実際に含まれるかまで照合する
- 照合は曖昧一致（類似度）にせず、**正規化後の部分文字列一致**とする（空白・改行除去、全角/半角統一など。PDF抽出の改行ズレによる偽陰性を防ぐ）
- 構造的な対策として、回答が引用できるのは検索でヒットしたチャンクのみに制約する（生成後の検証より生成時の制約の方が強い）

## カード名解決

質問中のあいまいな表記を、公式の正式名称と `card_id` に確定する工程（`resolve_card_name()`）。裁定の正しさは「どのカードの話か」が決まっていないと成り立たないため、パイプラインの最初の関門とする。

例: 「赤ゾ」「レッドゾーン」→ 《轟く侵略 レッドゾーン》など。

### 手順

1. 質問からカードっぽい語句を抜き出す
2. ローカルの略称辞書（略称→候補リストの1対N）を引く
3. なければ公式カード検索（必要ならweb検索）で候補を取る
4. 候補ごとに詳細GETして正式名を確認する
5. 結果に応じて分岐する

| 候補数 | 動作 |
|--------|------|
| 1件 | 正式名＋`card_id` で自動確定 |
| 複数 | 推測せずユーザーに確認（`clarify`） |
| 0件 | 候補提示または正式名の再確認を依頼 |

実装メモ（MVP）:

- 入力は先にクエリ掃除（`Nコス`・レア表記など検索ノイズを除去）。属性での候補絞り込みは専用入力がないため行わない（曖昧なら `clarify`）
- 読み仮名とラテン正式名のギャップは略称辞書シードで埋める（例: ドラッヘダーバンデ → 俳句爵 Drache der'Bande）
- 公式ヒットはあるが名前キー不一致のときは not_found にせず `clarify`（または suggestions）へ落とす
- 辞書が省略するのは検索であって確認ではない。1対1で保存すると最初に解決した1枚に誤って固定されるため、常に1対N（候補リスト）で持つ

### 検索コストの制約（UIをステップ化した理由）

公式アクセスは自前で直列＋最低約0.4秒間隔（公式が2秒を義務付けているわけではない）。
カード詳細はキャッシュヒット時は公式へ行かない。`buildOfficialSearchVariants` は中黒補完・接頭辞短縮で
最大12語を試すため、0件が続くクエリではなお数秒かかりうる。
そのうえで読み仮名（例: ひらがな表記の読み）は漢字正式名と文字列一致しないので、
**空打ちを重ねた末に失敗する**のが最悪パターンだった。

- 個別カードの別名シードで塞ぐのは不採用（聞き返しを隠すだけで再発する）
- 仮名の表記ゆれ対策は「原文を捨てず候補を1つ足す」形なら安全
  （正式名がひらがなのカードがあるため、カタカナへの**上書きは不可**）
- マナ列挙の抽出は、マナのマーカー（「マナに」等）が無ければ何も返さない。
  質問全文を候補にすると文の断片をカード名として公式検索し、略称辞書も汚す
- 抜本策は `正式名 → card_id` のローカル名前索引だが、一覧HTMLに名前がなく
  全件は詳細GETが必要（約2万枚 × 2秒 ≒ 一晩のバッチ）。オフライン前提・
  公開時のサイトポリシー確認が必要なため**保留**。索引は略称の曖昧性を解消しないので、
  送信前確定UIとは代替関係ではなく補完関係

## 会話フロー（送信前にカードを確定する2ステップ）

質問文からカード名を推定する方式は、表記ゆれ（読み仮名・ひらがな・略称）で解決に失敗し、
公式へのレート制限付き試行を積み上げた末に `not_found` で終わる。裁定は「どのカードの話か」が
決まらないと成り立たないので、**推論に入る前にユーザーへ確定させる**。

```
ステップ1: 状況を書く（自由文）
  → 「カード選択へ」（送信ボタンの代替。位置・色・矢印は送信と同じ）
ステップ2: カード確定ポップアップ（2/2）
  ├─ 検索窓は原則空で開く（質問文からの語句自動挿入はしない）
  ├─ 検索 → 候補グリッド → 選択でチップ化（複数枚）。選択時は窓をクリアして次入力へ
  ├─ 1枚だけで進むときは「他にありませんか？」の弱い確認（枚数だけの一律確認）
  ├─ 質問文も畳んだ表示から編集できる（閉じずに直せる）
  └─ 「特定のカードなし」を明示的に押した場合のみカード0枚で進める
  → 本送信（question + 確定した card_id[]）
  → 能力取得 → ルール/Q&A検索 → 生成 → Evidence Gate
      ├─ OK → answer
      └─ NG → 再検索1回 → ダメなら withhold
```

### 方針

- **順序は「状況 → カード」**。先に状況を書くほうが、関わるカードがユーザー自身の中で整理される
- **カード選択は原則必須**。未確定のまま推論に入ると解決試行でタイムアウトしうる。
  カード不要な一般ルール質問は、こちらが動的に判定せず**専用ボタンをユーザーに押させる**
- **カード欄は常設しない**。使うのは確定の一瞬だけなので、その間だけ画面を広く占有してよい
- **候補は縦スクロールのグリッド**。広い面積では横スクロールは一覧性が落ちるため使わない
- **検索窓への質問文の自動挿入はしない**。誤った非カード語句が入り、略称の打ち直しもかえって面倒になる。
  clarify 等から「この語で開き直す」ときだけ初期語を渡す
- **検索直後は入力を残す**（伸ばし打ち・タイポ修正用）。**候補を選んだらクリアしてフォーカスを戻す**
- **質問文は自動書き換えしない**。正式名はプロンプト組み立て時に別フィールドで渡す
  （本文への自動挿入は挿入位置が不定・複数枚で冗長・再送で二重化するため）
- **候補0件はポップアップ内でリトライ**を完結させる（試した語を見せ、検索窓を残す）。
  ここが従来の `not_found` の置き換わり先
- ステップ表示はドット列（ステッパー）ではなく見出しの `（2/2）` で足りる。
  行き来できる設計とステッパーの一方向表現は噛み合わせが悪い

### `clarify`（従来経路）の位置づけ

送信前確定に寄せるため、推論中の `clarify` は例外扱いへ縮小する。残す場合も
**候補提示UIは送信前と同一コンポーネント**にして、「途中で聞き返された」感を出さない。

- **確認は1ターンにまとめる**。カードA・Bとも曖昧なら一度に両方聞く（逐次確認しない）
- **再開時は再検索しない**。`clarify` の候補に載せた `card_id` / `detail_url` を使い、能力取得以降から続ける
- **「わからない」** → MVPでは `withhold`（保留）し、正式名を指定しての再質問を促す。全候補への並列回答はしない
- 確認待ちセッションのTTLはMVPでは厳密に定めない（次メッセージまで保持／再起動で消える程度でよい）

### 保持する状態（確認待ち中）

| 項目 | 中身 |
|------|------|
| `original_question` | 最初の質問文 |
| `pending_clarifications` | 未解決の略称と候補リスト（`card_id` 付き） |
| `resolved_cards` | すでに1件に確定したもの |
| `status` | `awaiting_clarify` / `running` / `done` |

## 情報ソース

### 公式（論拠として使用可）

- カードDB: https://dm.takaratomy.co.jp/card/ （詳細: `/card/detail/?id=...`）
- よくある質問（裁定Q&A）: https://dm.takaratomy.co.jp/rule/qa/ （記事: `/rule/qa/{id}/`、旧: `/rule/qa_old/`）
- 公式ルール（総合ルールPDF）: https://dm.takaratomy.co.jp/rule/rulechange/ から配布（例: `/img/dm_rule_YYYYMMDD_*.pdf`）

### 有志wiki（補助のみ）

- 論拠・出典としては使用しない
- 許容する用途: 類似Q&Aの発見、カード正式名の候補提示
- 最終回答の引用は `dm.takaratomy.co.jp` のみとする
- フリーライド懸念への対応: wikiを参照しても出典は公式のみと明示する

## 回答の品質要件

- すべての回答に論拠と出典（公式URL）を付ける
- 公式Q&Aに該当がない場合は、確信度を段階的に明示する
  - 例: 「公式Q&Aに該当なし。ルールからの推論ですが、確定裁定ではありません」
- カード名が曖昧な場合（例: 「赤ゾ」→ 複数候補）は、推測で進めずユーザーに確認する
- 公式裁定の代替ではない旨を免責として表示する（大会ではジャッジに確認を）

## エラーハンドリング

| 状況 | 対応 |
|------|------|
| カード名が特定できない | 候補を提示してユーザーに確認 |
| 公式DBに該当カードなし | 正式名称の再確認を依頼 |
| 公式Q&Aに該当なし | ルールから推論し、不確実性を明示 |
| 出典検証に失敗 | 追加検索を試行。それでも不可なら回答を保留 |

## RAGデータの方針

- **ルール・Q&A**: ローカルミラー＋定期更新
- **カードDB**: 全件ミラーはしない。質問時に都度取得し、取得結果をTTL付きでローカルにキャッシュする（オンデマンドキャッシュ）

```
data/
  rules/          # 公式ルール（PDF/HTML）
  qa/             # 公式Q&A
  cards/          # カードのオンデマンドキャッシュ（質問されたカードのみ蓄積）
  aliases/        # 略称→候補リストの辞書（1対N。検証日時付き）
  meta/
    last_synced_at.json   # 最終同期日時（ユーザーへの信頼性表示に使う）
    content_hashes.json   # コンテンツ変更検知用
```

都度web取得のみにしない理由: 遅延、サイト構造変更による障害、レート制限のリスクがあるため。

### カードのオンデマンドキャッシュ

- キャッシュに入るのは実際に質問されたカードのみ。カード総数（2万枚超）に関わらず、サイズは「質問されたカードの種類数」でしか増えない
- 裁定質問は環境カード・挙動がややこしいカードに集中する（ロングテール分布）ため、ヒット率は高くなる見込み
- TTLは30日程度を想定。カードテキストはエラッタ以外ほぼ変わらないため長めでよい
- 保存場所はアプリが動くサーバー（または自分のPC）のディスク。サーバー側で持つことで全ユーザーがキャッシュを共有できる

## 公式サイトへの配慮・法務

- 取得時は必ずレート制限を入れる（直列＋数百ms間隔。悪用回避の最低限。同一カードはキャッシュで回避）
- ユーザー向けの本命ガードは「確定カードUIで無駄打ちを減らす」＋キャッシュ共有。公開時は `/api/cards` のIP単位制限も検討
- タカラトミーのサイトポリシーは権利者の許諾のない複製・転載・再配布を禁じている。個人利用（非公開）と、課金を伴う公開サービスでは法的リスクが大きく異なる
- **公開・課金の前に `dm.takaratomy.co.jp` のサイトポリシーを精読し、必要なら問い合わせる**（Phase 1 → Phase 2 の間の必須工程とする）

## 公式ルールの索引

独自索引を実装する。段階的に拡張する。

1. **v1**: 見出し単位のチャンク分割 + キーワード検索 + ルール番号のメタデータ付与（ルール番号は正規表現で機械的に抽出でき実装コストが低く、引用精度に直結するためv1に含める）
2. **v2（一部実装）**: キーワード能力名の静的辞書（`web/src/lib/rules/keywordDictionary.ts`）。質問に「侵略」「革命チェンジ」「ニンジャ・ストライク」「Zラッシュ」等が出たら、対応する総合ルール節を検索結果へ無条件注入する。曖昧検索の漏れを防ぐ。検索プランの `cardMentions` にキーワード能力名が混入した場合はカード解決対象から除外する（カード名ではない）
3. **v2.5（実装済）**: 論点オントロジー（`web/src/lib/rules/ontology/`）。`IssueKind` → `RuleConcept`（`ruleRefs` / `qaSeeds` / 任意の決定的 validator）を束ね、検索へ強制注入する。LLMに汎用ルールを毎回推論させない
4. **v3**: Q&A同士の「類似例」リンクをグラフ索引として活用。加えて、シナリオ検証で引用Q&Aの前提と本件の差分（`precedentDiffs`）を列挙し、結論だけの誤流用を抑止する
5. **視点固定（実装済）**: 「自分／相手」は能力コントローラー視点。強制選択カード（例: 同期の妖精）では錨となる公式Q&A（例: 43917）を検索結果へ強制注入し、検証器で `perspectiveChecks` を行う。issue registry（`classifyIssues`）経由で ontology と接続する

### RuleConcept の追加手順

新しい汎用論点を足すときは、カード個別の if ではなく次の順で束を増やす。

1. `IssueKind` と検出条件を `classifyIssues`（または専用 matcher）に追加する
2. `concepts.ts` に `RuleConcept`（`ruleRefs` / `qaSeeds` / `validatorId`）を登録する
3. 決定的に解けるなら `validators/` に純関数を追加し、`runValidators` から呼ぶ
4. 評価ケースを `docs/eval/` に1件以上置き、単位テストまたは `scripts/smoke-*.ts` で回帰する

## モデル

### 選定基準

テスト用の質問セット（20〜50問）で以下を比較して決定する。

- 正答率（公式Q&Aとの一致）
- ハルシネーション率（存在しない裁定の捏造がないか）
- 出典フォーマットの遵守
- レイテンシ・コスト

### テストセットの作り方

公式Q&A自体が「質問と正解のペア」なので、手作りせず自動生成する。ミラーしたQ&Aの一部をホールドアウト（検索対象から除外）してテスト問題にすることで、「答えを検索でカンニングできない状態で、ルールからの推論だけで正解できるか」を測定できる。

採点方法・合格ラインの詳細は `docs/evaluation.md`。

### モデル切替

- デフォルトは1モデル（コスパいいやつ）
- 切替は「高度な設定」内に配置し、UIに「実験的機能。通常はデフォルト推奨」と明記
- 一般ユーザー向けに大々的に設置しない

## 検討していること

### 有志wikiを含めるか

→ **補助用途に限定。論拠には使わない。**（上記「情報ソース」参照）

### モデル切替

→ **高度な設定に押し込む。** 一般ユーザーへの大々的な設置は避ける。裁定確認はAI性能検証としても有用なので、開発者・上級者向けに残す。

### 3モデル比較モード

異なる3つのモデルがそれぞれ回答する。MVPには含めない（後回し）。

- メリット: 信頼性の可視化、性能検証
- デメリット: コスト増、UXの複雑化
- 導入タイミング: Phase 2（開発者向け裏機能として）

### 3モデル合議モード

比較モードでそれぞれが出した結論に対して議論し最終結論を出す。比較モード使用後のみ選択可能。MVPには含めない。

- 合議は「3モデルが常に別々に答える」より、「不一致点だけを議論させる」方がコスト効率が良い
- 導入タイミング: Phase 3

### 用いるモデル

テストして決定する。（上記「モデル」参照）

### RAGドキュメントの置き場

→ **ルール・Q&Aはローカルミラー、カードは都度取得＋TTL付きオンデマンドキャッシュ。**（上記「RAGデータの方針」参照）

### 公式データの利用と法務リスク

→ **MVP（非公開）ではキャッシュ利用にとどめ、公開・課金前にサイトポリシー精読＋必要なら問い合わせ。**（上記「公式サイトへの配慮・法務」参照）。クレジット制の位置づけ（収益化かコスト自衛か）によってリスクの大きさが変わるため、あわせて決める

### 公式ルールに独自の索引機能を実装するか

→ **実装する。v1はシンプルなチャンク分割＋ハイブリッド検索から。**（上記「公式ルールの索引」参照）

### ゲーム進行ステップ駆動の裁定推論に切り替えるか

→ **狭い validator の積み上げでは足りない。別ブランチで最小スパイクする方針。**  
時系列クラス（TP優先無視・110.5a 無視）は、原則プロンプトでも「バトル／手札」短絡でも再発する（封印メタ／山札下メタ×出た時など）。  
デュエマ全体を if 分岐で書き切るのも非現実的なので、master の応急手当と切り離し、`出す時＋同時誘発＋101.4a` だけを実験ブランチで試す。  
記録: `docs/inference_approaches.md`

## 開発フェーズ

| フェーズ | 内容 |
|----------|------|
| Phase 1（MVP） | 単一モデル + 公式ソースのみ + 出典必須。公式Q&Aホールドアウトによるテストセットで正答率・ハルシネーション率を測定 |
| Phase 1→2 の間 | 公開・課金に向けた法務確認（サイトポリシー精読、必要なら問い合わせ） |
| Phase 2 | 高度な設定（モデル切替）、3モデル比較モード |
| Phase 3 | 3モデル合議モード（不一致時の条件付き発動など） |

## 継続改善

- 誤回答・不確実な回答をログに蓄積し、テストセットにフィードバックする
- 新弾発売前後はQ&Aが増えるため、定期同期を行う
- 略称辞書は新弾で候補が増えうる（例: レッドゾーン系）。定期同期のタイミングで候補リストを引き直す
- 新弾カードは公式Q&Aが未整備のことがある。「このカードの公式Q&Aはまだ存在しない」ことを検出し、確信度表示に反映する
- `last_synced_at` をユーザーに表示し、情報の鮮度を示す
