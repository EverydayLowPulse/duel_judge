## 1. 何を作るか

デュエル・マスターズの裁定質問に答えるWebアプリ。
「このカードとこのカードがこうなったとき、どうなる？」という質問に対して、**公式の情報だけを根拠に**、出典付きで答える。

守ること:

- **根拠は公式のみ。** 公式カードDB、公式Q&A、総合ルールだけを出典にする
- **根拠がなければ答えない。** 出典を示せないときは回答を保留する（`withhold`）
- **どのカードの話かを先に確定する。** カードが曖昧なまま推論しない
- **公式裁定の代わりではない。** 免責を必ず表示する（大会ではジャッジに確認してもらう）

## 2. 全体の流れ

### ユーザーから見た流れ

1. 状況を文章で書く
2. 関係するカードを検索して選ぶ（[4章](#4-カードの確定)）
3. 回答が出る。結論、推論、根拠（公式URLと引用文）、確信度が表示される

### 内部の処理

1回のプロンプトにすべてを詰め込まず、段階ごとに処理を分ける。

```
質問 ＋ ユーザーが確定したカード
  │
  ├─ 1. カード情報の取得 …… 公式DBから能力テキストなどを取る
  ├─ 2. 検索プラン ……………… 質問を「固有名・出来事・ルール概念」に分け、検索語を作る
  ├─ 3. 事実の整理 ……………… 質問が述べている状況を構造化する（ScenarioFacts）
  ├─ 4. 論点の分類 ……………… マナ支払い・視点・待機・処理順など、何が争点かを判定する
  ├─ 5. 公式ソースの検索 …… Q&Aと総合ルールを複数の語で検索し、統合・並べ替える
  ├─ 6. 機械判定 ………………… 純関数で白黒つく論点はここで判定する（validator）
  ├─ 7. 追加の検証 …………… 処理順・宣言条件・視点などをLLMで確認する（関係するときだけ）
  ├─ 8. 回答の生成 …………… LLMが根拠付きのJSONを返す
  └─ 9. 出典検証 ……………… 引用が取得済みテキストに本当にあるかを照合する（Evidence Gate）
        ├─ 通過 → 回答を表示
        └─ 失敗 → 同じ検索結果のまま1回だけ再生成 → それでも失敗なら保留
```

6で「不可能」と確定した場合は、LLMを呼ばずに総合ルールの引用付き回答を組み立て、9へ進む。

### 各段階の実装

| 段階 | 関数 | ファイル（`web/src/lib/` 以下） |
|------|------|------|
| 全体の進行 | `runJudge` | `judge/runJudge.ts` |
| 1. カード情報の取得 | `buildConfirmedScenarioCards` / `fetchCardDetail` | `judge/scenarioCards.ts` / `official/card.ts` |
| 2. 検索プラン | `planSearchWithGemini` | `llm/searchPlanner.ts` |
| 3. 事実の整理 | `buildEnrichedScenarioFacts` | `judge/facts/` |
| 4. 論点の分類 | `classifyIssues` | `judge/issues/classifyIssues.ts` |
| 5. 公式ソースの検索 | `retrieveOfficialSources` | `judge/retrieveSources.ts` |
| 6. 機械判定 | `runValidators` / `buildDeterministicAnswer` | `judge/validators/` |
| 7. 処理順の確認 | `verifyResolutionOrderWithGemini`（起動判定は `isOrderRelevant`） | `llm/resolutionOrderVerifier.ts` / `judge/resolutionOrder.ts` |
| 7. 宣言条件・視点・前例との差 | `verifyScenarioWithGemini` | `llm/scenarioVerifier.ts` |
| 8. 回答の生成 | `generateAnswerWithGemini` | `llm/gemini.ts` |
| 9. 出典検証 | `runEvidenceGate` | `answer/evidenceGate.ts` |

関数名に `Gemini` と付いているものは、初期実装の名残り。実際にはユーザーが選んだモデル（Gemini / DeepSeek）で動く。

### 各段階のルール

- **検索プラン（2）**: LLMの出力は検索語づくりにだけ使う。回答の根拠にはしない
- **カード情報（1, 3）**: カードの種類・文明・パワー・コスト・種族・能力テキストは公式DBの値で上書きする。名前が一致しない近い候補は採用しない。LLMが推測した値は機械判定に渡さない
- **論点の分類（4）**: 検出した論点から、関係する総合ルール番号（`ruleRefs`）と公式Q&A（`qaSeeds`）を引き、検索結果に必ず含める（[6章](#6-総合ルールの索引と論点)）
- **公式ソースの検索（5）**: 検索プランが作った、Q&A用と総合ルール用の複数の検索語で引く。Q&Aは公式サイトの検索（`qa_w`）、総合ルールはローカルの索引を使う。重複をまとめてから並べ替える
- **機械判定（6）**: 例は多色マナの支払い。判定できないときや、他の論点が残るときは、判定結果を制約文としてLLMに渡す
- **処理順の確認（7）**: 「どの順で解決されるか」が論点のときだけ起動する。質問に関係する開始点から、誘発と解決のキューを短くまとめて後段に渡す。処理順の原則の全文はこの段階のプロンプトにだけ入れ、回答生成のプロンプトには積まない
- **宣言条件（7）**: 能力を使うと宣言した時点のクリーチャーで、文明・種族・コスト・パワーの条件を判定する。後から進化したり効果で条件を満たしたりしても、宣言時点にさかのぼって許可しない

### 推論の考え方

いまの推論は、**ゲームの進行をシミュレートしていない。**
論点を検出し、関係する原則を制約として与えたうえで、LLMに当てはめさせている（論点駆動）。
この方式の限界と、盤面を状態機械で追う方式（StepEngine）の検討は [inference_approaches.md](./inference_approaches.md) にまとめた。

## 3. 出典検証（Evidence Gate）

LLMの回答を表示する前に、機械的にチェックする最後の関門。詳しいルールは [answer_format.md](./answer_format.md#evidence-gate出典検証)。

考え方:

- **引用がない回答は出さない**
- **URLの実在だけでは足りない。** 実在するページに、存在しない裁定を紐付けるハルシネーションを防げないため、引用文がそのページの取得済みテキストに含まれるかまで照合する
- **照合は曖昧一致にしない。** 類似度ではなく、正規化した後の部分文字列一致で判定する。正規化では空白・改行を除き、全角と半角をそろえる。PDF抽出で改行の位置がずれても誤って落とさないため
- **そもそも検索でヒットしたテキストしか引用させない。** 生成後に検証するより、生成時に制約するほうが強い

## 4. カードの確定

裁定は「どのカードの話か」が決まらないと成り立たない。そのため、推論に入る前にカードを確定させる。

### なぜユーザーに選ばせるのか

最初は、質問文からカード名を推定していた。しかし次の理由でうまくいかなかった。

- **表記ゆれが多い。** 略称（例: 「赤ゾ」）、読み仮名、ひらがな表記などは、公式の正式名と文字列が一致しない
- **公式検索が遅い。** 公式サイトへは自前のレート制限で直列、最低0.4秒間隔でアクセスしている。さらに1つの語に対して、中黒の補完や前方の短縮で最大12通りの検索語を試すので、ヒットしない語では数秒かかる
- **最悪のパターン。** ヒットしない検索を何度も重ねたうえで、結局「見つからない」で終わる

個別のカードの別名を辞書に登録して塞ぐ方法は採らなかった。聞き返しが起きにくくなるだけで、別のカードで同じ問題が再発するため。

そこで、**送信前にユーザー自身にカードを選んでもらう**2ステップの画面にした。

### 画面の流れ

```
ステップ1: 状況を書く（自由文）
  └─「カード選択へ」ボタン（送信ボタンと同じ位置・色・矢印）

ステップ2: カード確定ポップアップ（見出しに「2/2」）
  ├─ 検索窓は空で開く
  ├─ 検索 → 候補がグリッドで出る → 選ぶとチップになる（複数枚選べる）
  ├─ 1枚だけで進もうとすると「他にありませんか？」と軽く確認する
  ├─ 質問文は折りたたんだ表示から、閉じずに編集できる
  └─「特定のカードなし」を押したときだけ、カード0枚で進める

送信（質問文 ＋ 確定したカードの card_id の一覧）
  └─ 能力の取得 → 検索 → 生成 → 出典検証
```

### 画面の設計判断

| 決めたこと | 理由 |
|------------|------|
| 順番は「状況 → カード」 | 先に状況を書くと、関わるカードがユーザーの中で整理される |
| カード選択は原則必須 | 未確定のまま推論すると、名前の解決でタイムアウトしうる |
| カードが不要な質問は、ユーザーが「特定のカードなし」を押す | 一般ルールの質問かどうかを、アプリ側で自動判定しない |
| カード欄は常に表示しない | 使うのは確定する一瞬だけなので、その間だけ画面を広く使ってよい |
| 候補は縦スクロールのグリッド | 広い面積で横スクロールにすると、一覧しにくい |
| 検索窓に質問文の語句を自動で入れない | カードではない語が入りやすく、消して打ち直すほうが面倒。聞き返し（`clarify`）から開き直すときだけ初期値を入れる |
| 検索した直後は入力を残す | 続けて打ったり、打ち間違いを直したりできるように |
| 候補を選んだら入力を消し、検索窓にフォーカスを戻す | 次のカードをすぐ探せるように |
| 質問文を自動で書き換えない | 正式名はプロンプトを組み立てるときに別の欄で渡す。本文に挿入すると、位置が定まらない・複数枚で冗長になる・再送で二重になる |
| 候補0件のときはポップアップの中でやり直させる | 試した語を見せ、検索窓を残す。以前の「見つかりませんでした」で終わる応答の代わり |
| 進捗は「2/2」の見出しだけ | ステップを行き来できる設計なので、一方向に進むステッパー（ドット列）とは相性が悪い |

### 名前解決の仕組み

ユーザーが検索窓に入れた語を、公式の正式名と `card_id` に結び付ける処理（`resolveCardName`、`resolve/resolveCardName.ts`）。
例: 「赤ゾ」「レッドゾーン」→《轟く侵略 レッドゾーン》など。

手順:

1. 検索語から雑音を除く（「Nコス」、レアリティ表記など）
2. ローカルの略称辞書を引く
3. 辞書になければ公式カード検索で候補を取る。公式で0件なら有志wikiで正式名の候補を探し、公式で引き直す
4. 候補ごとに詳細ページを取り、正式名を確認する
5. 候補の数で分岐する

| 候補の数 | 動作 |
|----------|------|
| 1件 | 正式名と `card_id` で確定する |
| 複数 | 推測せず、ユーザーに選んでもらう |
| 0件 | 近い候補を示すか、正式名を確認してもらう |

実装上の注意:

- **略称辞書は1対N（略称 → 候補リスト）で持つ。** 辞書で省くのは「検索」であって「確認」ではない。1対1で保存すると、最初に解決した1枚に誤って固定される
- **読み仮名と、ラテン文字を含む正式名との差は、略称辞書のシードで埋める。** 例: ドラッヘダーバンデ → 俳句爵 Drache der'Bande
- **公式検索はヒットしたが名前が一致しないときは「見つからない」にしない。** 候補として示す
- **属性（文明やコストなど）での絞り込みはしない。** 専用の入力欄がないため。曖昧なら候補を示す
- **仮名の表記ゆれ対策は、元の語を残したまま候補を1つ足す形にする。** 正式名がひらがなのカードがあるので、カタカナへ置き換えてはいけない
- **マナゾーンの列挙を抜き出すときは、「マナに」などの目印がなければ何も返さない。** 質問文全体を候補にすると、文の断片をカード名として公式検索してしまい、略称辞書も汚れる
- **根本策は「正式名 → `card_id`」のローカル索引。** ただし公式の検索結果一覧にはカード名がなく、全件の詳細ページを取る必要がある。オフラインのバッチになり、公開時のサイトポリシー確認も要るため保留している。なお索引ができても略称の曖昧さは解消しないので、送信前の確定画面の代わりにはならない（補い合う関係）

### 聞き返し（`clarify`）の扱い

推論の途中でカードを聞き返す経路は、送信前の確定画面ができたので例外扱いに縮小した。残す場合のルール:

- **候補を見せる部品は、送信前の確定画面と同じものを使う。** 「途中で聞き返された」と感じさせない
- **確認は1回にまとめる。** カードAもBも曖昧なら、一度に両方聞く
- **再開するときに検索し直さない。** 聞き返しの候補に載せた `card_id` と詳細URLを使い、能力の取得から続ける
- **「わからない」と答えられたら保留する。** 正式名を指定して質問し直すよう促す。全候補について並べて答えることはしない
- **確認待ちの保持期間は厳密に決めない。** 次のメッセージまで、またはサーバー再起動まで持てばよい

確認待ちの間に持つ状態（設計のみ。未実装）:

| 項目 | 中身 |
|------|------|
| `original_question` | 最初の質問文 |
| `pending_clarifications` | 未解決の略称と候補リスト（`card_id` 付き） |
| `resolved_cards` | すでに1枚に確定したカード |
| `status` | `awaiting_clarify` / `running` / `done` |

## 5. 情報ソースとデータ

### 使ってよい情報

| ソース | 用途 | 場所 |
|--------|------|------|
| 公式カードDB | 根拠にしてよい | https://dm.takaratomy.co.jp/card/ |
| 公式Q&A（よくある質問） | 根拠にしてよい | https://dm.takaratomy.co.jp/rule/qa/（旧Q&Aは `/rule/qa_old/`） |
| 総合ルール（PDF） | 根拠にしてよい | https://dm.takaratomy.co.jp/rule/rulechange/ で配布 |
| 有志wiki | **補助のみ。** 類似Q&Aを見つける、正式名の候補を出す | — |

最終回答の引用は `dm.takaratomy.co.jp` だけにする。wikiを参照しても、出典は公式だけだと明示する（wikiへのただ乗りにならないように）。

各サイトからの具体的な取得方法は [research_official_sources.md](./research_official_sources.md)。

### データの持ち方

公式サイトを毎回取りに行くだけにはしない。遅い、サイト構造の変更で壊れる、レート制限に引っかかる、のリスクがあるため。

| データ | 方針 | 現状 |
|--------|------|------|
| 総合ルール | ローカルに索引を作る | ビルド時にPDFから索引を作り、デプロイに同梱 |
| 公式Q&A | ローカルにミラーし、定期的に更新する | 質問ごとに公式を検索し、取得した記事をキャッシュ。ミラーと定期更新は未実装 |
| カード | 全件はミラーしない。質問されたカードだけキャッシュする | 方針どおり（有効期限30日） |
| 略称辞書 | 略称 → 候補リスト（1対N）。確認日時付き | 方針どおり |

```
data/
  rules/          # 総合ルール（PDF/HTML）
  qa/             # 公式Q&A
  cards/          # 質問されたカードだけのキャッシュ
  aliases/        # 略称辞書（1対N。確認日時付き）
  meta/
    last_synced_at.json   # 最終同期日時（情報の鮮度としてユーザーに見せる。表示は未実装）
    content_hashes.json   # 内容の変更検知用
```

カードを質問時にだけキャッシュする理由:

- カードは2万枚を超えるが、キャッシュは「質問されたカードの種類数」でしか増えない
- 裁定の質問は、環境で使われるカードや挙動がややこしいカードに集中する。なのでヒット率は高くなる見込み
- カードの文面はエラッタ以外ほぼ変わらないので、有効期限は30日と長めでよい
- 保存先はアプリが動くサーバー（または自分のPC）のディスク。サーバー側に置けば全ユーザーで共有できる

### 公式サイトへの配慮と法務

- **取得には必ずレート制限をかける。** 直列で数百ミリ秒の間隔を空ける。同じカードはキャッシュで再取得を避ける
- **ユーザー起因のアクセスを減らす本命は、カード確定画面とキャッシュの共有。** 公開するなら `/api/cards` にIP単位の制限も検討する
- **タカラトミーのサイトポリシーは、権利者の許諾のない複製・転載・再配布を禁じている。** 非公開の個人利用と、課金を伴う公開サービスでは、法的リスクが大きく違う
- **公開・課金の前に、`dm.takaratomy.co.jp` のサイトポリシーを精読し、必要なら問い合わせる。** Phase 1 から Phase 2 へ進む前の必須作業とする（[9章](#9-開発フェーズ)）

## 6. 総合ルールの索引と論点

### 索引の段階

独自の索引を作り、段階的に広げる。

| 段階 | 内容 | 状態 |
|------|------|------|
| v1 | 見出し単位でチャンクに分け、キーワード検索する。各チャンクにルール番号を付ける。ルール番号は正規表現で機械的に取れて安く、引用の精度に直結するのでv1に入れた | 実装済み |
| v2 | キーワード能力の辞書（`rules/keywordDictionary.ts`）。質問に「侵略」「革命チェンジ」「ニンジャ・ストライク」「Zラッシュ」などが出たら、対応する総合ルールの節を検索結果に必ず入れる。検索漏れを防ぐ。検索プランのカード名にキーワード能力名が混ざったら、カード名ではないので名前解決から外す | 一部実装 |
| v2.5 | 論点オントロジー（`rules/ontology/`）。論点の種類（`IssueKind`）ごとに、関係するルール番号・公式Q&A・機械判定（`RuleConcept`）を束ね、検索に必ず入れる。汎用ルールを毎回LLMに推論させないため | 実装済み |
| v3 | 公式Q&A同士の「類似例」リンクを、グラフ状の索引として使う。あわせて、引用したQ&Aの前提と今回の質問の違い（`precedentDiffs`）を列挙させ、結論だけを流用する誤りを防ぐ | 前提差の列挙のみ実装 |
| 視点の固定 | 「自分／相手」は能力を使うプレイヤーから見た視点とする。選択を強制するカード（例: 同期の妖精）では、基準になる公式Q&A（例: 43917）を検索結果に必ず入れ、検証段階で視点をチェックする（`perspectiveChecks`）。論点分類（`classifyIssues`）経由でオントロジーとつながる | 実装済み |

### 新しい論点を足す手順

カードごとの `if` 文は書かない。能力テキストのパターン、論点（`RuleConcept`）、総合ルールといった原則で書く。具体的なカード名を書いてよいのは、略称辞書のシード、`qaSeeds`、smoke / 評価ケースだけ。

1. 論点の種類（`IssueKind`）と検出条件を `classifyIssues`（または専用の検出関数）に足す
2. `rules/ontology/concepts.ts` に `RuleConcept`（`ruleRefs` / `qaSeeds` / `validatorId`）を登録する
3. 機械的に判定できるなら、`judge/validators/` に純関数を足し、`runValidators` から呼ぶ
4. 評価ケースを `docs/eval/` に1件以上置き、単体テストか `web/scripts/smoke/smoke-*.ts` で回帰を確認する

## 7. 回答の品質

- すべての回答に、根拠と出典（公式URL）を付ける
- 公式Q&Aに該当がないときは、確信度を下げて明示する。例: 「公式Q&Aに該当なし。ルールからの推論で、確定した裁定ではありません」
- カード名が曖昧なとき（例: 「赤ゾ」で複数の候補）は、推測で進めずユーザーに確認する
- 公式裁定の代わりではない旨を表示する

### うまくいかないときの動き

| 状況 | 動き |
|------|------|
| カード名が特定できない | 候補を見せてユーザーに選んでもらう |
| 公式DBにカードがない | 正式名の確認をお願いする |
| 公式Q&Aに該当がない | ルールから推論し、確信度を下げて不確かさを明示する |
| 出典検証に失敗した | 同じ検索結果のまま1回だけ再生成する。それでも通らなければ保留する |

## 8. モデル

### 選び方

評価セットで次を比べて決める（測り方は [evaluation.md](./evaluation.md)）。

- 正答率（公式Q&Aと一致するか）
- ハルシネーション率（存在しない裁定をでっち上げないか）
- 出典の形式を守るか
- 応答時間とコスト

### 切り替え

- 既定はコストパフォーマンス重視の Flash 系
- 画面から DeepSeek / Gemini を切り替えられる（複数プロバイダ対応のデモも兼ねる）
- 課金・クレジット制は採らない（リリースを前提にしないポートフォリオ用途のため）

## 9. 開発フェーズ

| フェーズ | 内容 |
|----------|------|
| Phase 1（MVP） | 単一モデル、公式ソースのみ、出典必須。評価セットで正答率とハルシネーション率を測る |
| Phase 1 → 2 の間 | 公開・課金に向けた法務確認（サイトポリシーの精読、必要なら問い合わせ） |
| Phase 2 | 詳細設定（モデル切替）、3モデル比較モード |
| Phase 3 | 3モデル合議モード（意見が割れたときだけ発動する、など） |

### 継続的な改善

- 誤った回答や不確かな回答を記録し、評価セットに足す
- 新弾の発売前後は公式Q&Aが増えるので、定期的に同期する
- 新弾で略称の候補が増えることがある（例: レッドゾーン系）。同期のときに略称辞書の候補を引き直す
- 新弾のカードは公式Q&Aがまだないことがある。「このカードの公式Q&Aはまだない」ことを検出し、確信度に反映する
- 最終同期日時（`last_synced_at`）をユーザーに見せ、情報の鮮度を示す

## 10. 決定事項と保留事項

| 論点 | 結論 | 詳細 |
|------|------|------|
| 有志wikiを使うか | 補助用途だけ。根拠にはしない | [5章](#使ってよい情報) |
| どのモデルを使うか | 評価セットで比べて決める | [8章](#8-モデル) |
| データをどこに置くか | ルールは同梱の索引。Q&Aはミラーが目標（現状は検索＋キャッシュ）。カードは質問されたものだけキャッシュ | [5章](#データの持ち方) |
| 公式データの扱いと法務 | デモや非公開の利用ではキャッシュにとどめる。公開前にサイトポリシーを精読し、必要なら問い合わせる | [5章](#公式サイトへの配慮と法務) |
| 総合ルールに独自の索引を作るか | 作る。v1はチャンク分割とキーワード検索から | [6章](#索引の段階) |
| 複数モデルの並列回答・合議 | MVPとデモの範囲外。コストもUXの複雑さも増える | [9章](#9-開発フェーズ) |
| ゲームの進行をステップごとに追う推論に切り替えるか | 狭い機械判定を積み上げるだけでは足りない。別ブランチで最小の試作をする方針 | 下記 |

### ステップ駆動の推論について

時系列が絡む誤答が繰り返し出ている。具体的には、ターンプレイヤーの優先（総合ルール 101.4a）や、誘発した能力は発生源が離れても残る原則（110.5a）を無視する誤りで、原則をプロンプトに書いても、「バトルか手札か」の短絡的な機械判定を足しても再発する（例: 封印させるカードとバトルを強いるカードの組み合わせ、山札の下に送るカードと「出た時」能力の組み合わせ）。

一方で、デュエマ全体を `if` 文で書き切るのも現実的ではない。そこで、本番（master）の応急処置とは切り離し、「出す時の処理・同時に誘発した能力・101.4aの解決順」だけを実験ブランチで試す。詳しくは [inference_approaches.md](./inference_approaches.md)。
