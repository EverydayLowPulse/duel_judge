# 評価の設計

回答の精度をどう測り、どう採点するかのルール。
Phase 1（MVP）で「どのモデルを使うか」「公開してよいか」を決めるために使う。

実際の評価ケースとランナーの使い方は [eval/README.md](./eval/README.md)。

---

## 基本方針

**「たまに嘘をつくが正答率は高い」より、「正答率が少し低くても、でっち上げない」を優先する。**

裁定AIでは、自信満々の誤答のほうが「わかりません」より害が大きい。そのため採点は非対称にしていて、ハルシネーションは1件でもあれば不合格にする。

---

## 評価セット

### 2種類のセット

| セット | 作り方 | 測ること |
|--------|--------|----------|
| A. 直接Q&A | 公式Q&Aから問題を作る。正解のQ&Aが検索で見つかってよい | 普段の使い方に近い状態で、検索・引用・結論が公式と一致するか |
| B. ホールドアウト | 一部の公式Q&Aを検索対象から外し、ルールからの推論だけで答えさせる | Q&Aがないときに推論できるか。でっち上げずに確信度を下げたり保留したりできるか |

モデル選定ではAを主、Bを副として見る。

### 作り方

公式Q&Aはそのまま「質問と正解のペア」になっているので、問題は手作りせずQ&Aから作る。
セットBでは、使ったQ&Aを検索対象から外す。答えを検索でカンニングできない状態で、ルールからの推論だけで正解できるかを測るため。

- 評価している間は、ホールドアウトに使ったQ&Aを検索対象に戻さない
- 検索対象から外す仕組みは未実装

### 規模

合計20〜50問（A: 15〜40問、B: 5〜15問）が目標。いまは8問（[eval/](./eval/)）。

---

## 1問の書き方

```json
{
  "id": "eval-001",
  "set": "A",
  "question": "（ユーザーの質問文）",
  "gold": {
    "conclusion_summary": "結論の要約（人が1〜2文で書く）",
    "must_cite_urls": ["https://dm.takaratomy.co.jp/rule/qa/..."],
    "must_rule_refs": ["111.1"],
    "allowed_confidence": ["high", "medium"]
  },
  "notes": "採点時の注意（任意）"
}
```

- `must_cite_urls` と `must_rule_refs` は「最低限これは引用してほしい」リスト。ほかに正しい引用が増えても減点しない
- セットBでは `must_cite_urls` を空にし、ルール番号の引用や、`low` / `withhold` を期待してよい

## 採点

### 採点の軸

1問ごとに、各軸を人がYes/Noで判定する。部分点は付けない（裁定で「だいたい合っている」は危ないため）。

| 軸 | 合格の条件 | 落ちたら |
|----|------------|----------|
| 結論の一致 | `conclusion` が正解の結論と矛盾しない（言い回しの違いはよい） | 不正解 |
| 出典検証 | Evidence Gateを通っている（引用があり、照合が通り、URLが公式だけ） | 不正解 |
| 必須の出典 | `must_cite_urls` / `must_rule_refs` を満たす（セットAのみ） | 不正解 |
| ハルシネーション | 取得したテキストにない裁定、架空のURL、架空のルール番号を書いていない | **即不合格。1件でもアウト** |
| 確信度 | `confidence` が状況に合っている（直接のQ&Aがあるのに `low`、などは不可）。許容リストがあればその中 | 不正解 |
| 形式 | `answer` / `clarify` / `withhold` のどれかで、スキーマ違反がない | 不正解 |

**6つの軸をすべて満たした問題を「正答」とする。**

ルール番号を正解と完全に一致させることは求めない。見るのは `must_rule_refs` に書いたものだけ。

### 誰が採点するか

| 段階 | 方法 |
|------|------|
| Phase 1 の最初 | 人が採点する。基準のぶれを自分で見て直す |
| 問題が増えた後 | 人の判定を正とし、必要ならLLMによる採点（LLM-as-judge）を補助に使う。最終判断は人 |

LLMを最初から主な採点者にはしない。裁定の正誤にはドメイン知識が要るうえ、採点するLLM自身がハルシネーションしうるため。

ランナーの自動採点（`--full`）も補助の扱い。

## 集計する指標

| 指標 | 定義 | Phase 1 の目安 |
|------|------|----------------|
| 正答率 | 正答の数 ÷ 全問 | セットAで **70%以上** なら採用ライン |
| ハルシネーション件数 | 上の軸で即不合格になった件数 | **0件**。1件でもあれば、そのモデルは原則として採用しない |
| 出典検証の通過率 | Evidence Gateを通った回答の数 ÷ 回答しようとした数 | 参考。低ければ引用の設計が弱い |
| 不当な保留の率 | 答えられるはずなのに `withhold` した割合 | 参考。高すぎると使い物にならない |
| 応答時間とコスト | 1問あたりの秒数と概算の円 | 性能が同じなら安いほう |

---

## モデルを比べる手順

1. 同じ評価セットで、候補のモデルをすべて回す
2. ハルシネーションが1件以上あるモデルは、候補から外す（または検証し直す）
3. 残ったモデルで、正答率・コスト・応答時間を比べる
4. 既定のモデルを1つ決める

---

## 続けて評価する

- 本番（または自分で使っているとき）に出た誤答や不確かな回答を記録し、評価セットに足す
- 新弾の後は公式Q&Aが増えるので、セットAを定期的に入れ替える
