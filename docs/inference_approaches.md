# 裁定推論アプローチ（現状と実験候補）

裁定の正しさは「ルール知識の有無」だけでなく、**いつ・誰の効果が・どの順で・どの状態で解決されるか**の追跡に依存する。  
本書は現行パイプラインの実態と、将来試したいステップ駆動アプローチを記録する。

実装の正本フローは `docs/project.md`。ここは推論方式の設計メモ。

---

## 現状（master）: 論点駆動 + 原則制約 + LLM

ゲーム盤をシミュレートしてはいない。質問を構造化し、関係しそうな論点・原則を注入してから LLM に当てはめる。

```
質問（+ 確定カード）
  → 検索プラン（固有名・イベント・概念）
  → ScenarioFacts（主張された事実の構造化。カード属性は公式DBで上書き）
  → classifyIssues / RuleConcept（論点検出・原則・qaSeeds・ruleRefs）
  → 公式Q&A・総合ルール検索（シード強制注入）
  → 決定的 validators（解けるものは LLM なし）
  → （orderRelevant のときだけ）verify_resolution_order
       ※開始イベントを動的選択。原則は当該 system のみ。後段へ短い Observation
  → 残余: scenarioVerifier（宣言・視点・precedentDiffs）+ generateAnswer
  → Evidence Gate（引用必須・部分一致照合）
```

### 何を「追っている」か

| 層 | 役割 | 例 |
|----|------|----|
| Facts | 質問が主張する静的事実 | マナ帯、宣言時点パワー見積もり、入れ替え阻害 |
| Issues / Concepts | 論点タグと不変条件 | `pending_abilities`, `resolution_order`, `replacement_effect` |
| Validators | 純関数で可/不可 | 多色マナ支払い、入れ替え失敗 |
| 処理順 Observation | 関係区間だけの誘発/解決キュー | `windowStart` + 短い `constraintsForAnswer` |
| LLM 制約文 | 誤推論の禁止 | Observation 結果、宣言条件など |
| Evidence Gate | 出典の正当性 | チャンク外の捏造を拒否 |

エントリは `web/src/lib/judge/runJudge.ts`。論点レジストリは `classifyIssues.ts`、概念束は `rules/ontology/concepts.ts`。  
処理順フェーズは `web/src/lib/llm/resolutionOrderVerifier.ts`。

### master に入った処理順フェーズ（スコープ付き LLM Observation）

- **フル状態機械ではない**。質問に関係する開始点から、誘発と解決・101.4a・最終情報を Observation するだけ
- 原則全文を `generateAnswer` へ常時積み増ししない（プロンプト肥大を避ける）
- 起動は安価な `orderRelevant` ゲート。無関係な質問では呼ばない
- StepEngine（出す時＋同時誘発＋101.4a を決定的に回す）は **別ブランチ実験のまま**（下記）

### 長所

- 実装コストが比較的低い（盤面エンジンを書かない）
- 公式テキスト＋Q&A を根拠にしやすい（Evidence Gate と相性が良い）
- 論点ごとに smoke / eval を足して回帰しやすい
- 解けないケースは withhold / confidence で逃げられる
- 処理順原則を専用フェーズに閉じられる

### 短所（時系列クラスの誤答が繰り返し出る）

- **時系列を1本の状態機械として持たない**ため、Observation が浅いと「誘発したか」と「解決時に行動できるか」をなお混同しうる
- ターンプレイヤー / 非ターンプレイヤーの解決順（総合ルール 101.4 / 101.4a など）を、**決定的手順として実行してはいない**（LLM Observation）
- 対策が「原則テキスト／狭い validator／スコープ付き Observation」に寄り、漏れが出ると同型ミスが再発する
- 同時誘発・割り込み・置換の連鎖を、網羅的にではなく「よくある誤読」単位で塞いでいる

#### 実害ログ（同じ根因）

| シナリオ（要旨） | 誤答 | 足りないもの |
|------------------|------|--------------|
| 踏み倒し出 → 場のバトルメタ → 出た時で封印 | 「封印されたからメタは誘発しない」 | 誘発と解決の分離（110.5a）。封印は解決時のバトル不能 |
| 場の山札下メタ → 出た時封印クリーチャー | 「山札下に置かれたから出た時（封印）は解決しない」＋順序無視 | 101.4a（TP先）と 110.5a（発生源が離れても待機は残る） |

どちらも「知識が無い」より **進行を追っていない** のが原因。

### 対症療法の限界（重要）

`seal_pending_resolve` のような決定的短絡で「バトルさせ／手札戻し」を分けても、それは **110.5a の一例の言い換え**に過ぎない。

- デュエマの分岐は「バトルか手札か」では表せない（山札下・破壊・入れ替え・選択不能・置換・使用宣言など）
- 個別パターンを validator で増やし続けるのは、実質ルールエンジンの手書きであり **スケールしない**
- 一方、原則をプロンプトに書くだけでは LLM が無視する（上記ログ参照）

結論: **狭い決定的分岐の積み上げでデュエマ全体を倒すのは無理がある**。  
master の対症療法は「既知の地雷の応急手当」に留め、根本はステップ駆動（またはそれに近い必要最小エンジン）側で試す。

## 将来実験候補: ステップ駆動（ゲーム進行シミュレーション）

### 狙い

質問のシナリオを、総合ルールの進行に沿って短いタイムラインに展開する。

1. どのステップ／サブステップか（出す・攻撃宣言・ブレイク前後 など）
2. 誰がターンプレイヤーか
3. その瞬間に誘発する能力を列挙し、待機キューへ入れる
4. 101.4a に従い、S・トリガー系 → ターンプレイヤーの待機 → 非ターンプレイヤーの待機、の順で1件ずつ解決
5. 各解決の前後でゾーン・無視（封印）・選択可否などの状態を更新
6. 最後に「ユーザーの問い」に対する観測結果だけを回答生成へ渡す

こうすると、「誘発したか」「待機は残るか」「解決時にバトルできるか」が**別イベント**として自然に分かれる。

### 想定モジュール（案）

別ブランチでの試作を想定。master の本番パイプラインをいきなり置き換えない。

```
ScenarioFacts
  → TimelineBuilder（質問 → 粗いイベント列。不足は clarify）
  → StepEngine（状態 + pending queue + 101.4a スケジューラ）
  → Observation（問いに対応する事実: triggered / resolved / fizzled / reason）
  → 既存の retrieve + Evidence Gate + 回答生成
```

- StepEngine は可能な範囲で決定的にする（カード固有IFは書かない。能力テキストのパターン／キーワードで分岐）
- LLM は「曖昧な質問のイベント列起こし」と「Observation → 自然文」に限定し、途中のルール適用はエンジン側
- AGENTS.md どおり、個別カード名分岐は検出・結論・プロンプトに入れない（smoke / qaSeeds / 略称のみ）

### リスク・不確定性

- 総合ルール全体の再現は大きい（攻撃ステップ、ブレイク、置換、使用宣言、状況起因など）
- 質問文は盤面の完全情報を含まない → 前提不足時の clarify 設計が必須
- 成功してもレイテンシ・保守コストが増える可能性
- 「部分シミュレータ（出す時＋同時誘発だけ）」に絞らないと完走しにくい

そのため **成功は不確定**。本番採用前に別ブランチでスパイクし、封印×メタ／革命チェンジ後の待機／置換ブレイクなど既存 smoke で比較する。

### 実験手順（後でやるとき）

1. ブランチ例: `experiment/step-engine`（名称は任意）
2. MVP スコープを「バトルゾーンに出た時の同時誘発＋101.4a 解決」に限定
3. Observation を既存 `scenarioAnalysis` に差し込んで A/B（同じ eval セット）
4. 正答率・withhold 率・レイテンシを記録し、adopt / park / reject を決める
5. adopt 時だけ `project.md` の処理フローを更新し、master へ統合

### 現状への影響

- master では論点駆動＋既知地雷の応急手当＋**スコープ付き処理順 Observation** を継続する（完全解ではない）
- Observation でも時系列クラスの誤答が残るなら、別ブランチ `experiment/step-engine` で **出す時＋同時誘発＋101.4a だけ**をスパイクする価値が高い
- フルルールエンジン化や「validator の無限増殖」は採用しない
- 本ファイルは方針メモ。スパイク着手は明示的に決めてから

### スパイクの成功条件（最小）

次の2問を、カード名ハードコードなしで Observation まで機械的に出せること。

1. 封印×バトルメタ: 誘発する／バトル解決は不発
2. 山札下メタ×出た時: TP側の出た時が先（または少なくとも「発生源が離れても出た時待機は残る」）

これ以外は最初から対象外。広げたくなったらスコープを切り直す。
