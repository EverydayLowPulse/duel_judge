# 裁定推論のアプローチ（研究メモ / ADR）

いまの推論方式がどう動いていて、どこで限界が来ているか。そして将来試したい別の方式を記録する。

> このファイルは研究メモ。本番の処理フローの正本は [project.md](./project.md#2-全体の流れ) にある。
> 後半の「ステップ駆動」は採用済みの実装ではなく、将来の実験候補と失敗の記録。

## 要約

- **いま**: 質問から論点を検出し、関係する原則を制約として与えて、LLMに当てはめさせている（論点駆動）。ゲームの進行はシミュレートしていない
- **問題**: 「いつ・誰の能力が・どの順で解決されるか」が絡む質問で、同じ型の誤答が繰り返し出る
- **これまでの対策の限界**: 原則をプロンプトに書いてもLLMが無視する。誤答のパターンごとに機械判定を足すのは、ルールエンジンを手で書くのと同じでスケールしない
- **方針**: 本番の応急処置は続ける。根本対策として、進行を追う最小限のエンジン（StepEngine）を別ブランチで試す。まだ着手していない

## このメモで使う用語

| 用語 | 意味 |
|------|------|
| 誘発 | 能力の条件が満たされ、「解決待ち」になること |
| 解決 | 待っている能力を実際に処理すること。誘発と解決は別の出来事 |
| 待機 | 誘発して解決を待っている状態の能力 |
| ターンプレイヤー（TP） | そのターンを進めているプレイヤー |
| 101.4 / 101.4a | 総合ルールの、複数の能力が同時に待機したときの解決順の規定 |
| 110.5a | 総合ルールの、誘発した能力は発生源が場を離れても待機として残る規定 |
| Observation | 処理順を確認する段階が後段に渡す、短い観察結果 |

## 現状: 論点駆動 + 原則制約 + LLM

### 処理の流れ

```
質問 ＋ 確定したカード
  → 検索プラン（固有名・出来事・ルール概念に分ける）
  → ScenarioFacts（質問が述べる事実を構造化する。カードの属性は公式DBで上書き）
  → classifyIssues / RuleConcept（論点を検出し、原則・qaSeeds・ruleRefs を引く）
  → 公式Q&A・総合ルールの検索（シードを必ず入れる）
  → 機械判定（validator。解けるものはLLMを使わない）
  → 処理順の確認（処理順が論点のときだけ）
       開始点を質問から選び、原則はこの段階のプロンプトにだけ入れる。後段へは短い Observation を渡す
  → 残り: scenarioVerifier（宣言条件・視点・前例との差）と回答生成
  → Evidence Gate（引用必須。正規化後の部分一致で照合）
```

### 各層が受け持つもの

| 層 | 役割 | 例 |
|----|------|----|
| Facts | 質問が述べる、変化しない事実 | マナゾーンの中身、宣言時点のパワーの見積もり、入れ替えを妨げる要因 |
| Issues / Concepts | 論点の種類と、それに伴う不変の原則 | `pending_abilities`（待機）、`resolution_order`（処理順）、`replacement_effect`（置換） |
| Validators | 純関数で可否を出す | 多色マナの支払い、入れ替えの失敗 |
| 処理順の Observation | 関係する区間だけの、誘発と解決のキュー | 開始点（`windowStart`）と短い制約文（`constraintsForAnswer`） |
| LLMへの制約文 | 誤った推論の禁止 | Observation の結果、宣言条件など |
| Evidence Gate | 出典が正当か | 取得したテキストにない引用を拒否する |

主な実装（`web/src/lib/` 以下）:

- 全体: `judge/runJudge.ts`
- 論点の登録と検出: `judge/issues/classifyIssues.ts`
- 原則の束: `rules/ontology/concepts.ts`
- 処理順の確認: `llm/resolutionOrderVerifier.ts`

### 処理順の確認段階（master に入っているもの）

- **完全な状態機械ではない。** 質問に関係する開始点から、誘発と解決、101.4a、最後の状態を観察するだけ
- **処理順の原則を、回答生成のプロンプトに毎回積まない。** プロンプトが膨らむのを避けるため
- **起動の判定は安い。** `isOrderRelevant` が処理順と無関係だと判断した質問では呼ばない
- StepEngine（出す時の処理・同時誘発・101.4a を機械的に回す）は、別ブランチの実験のまま（後述）

### 長所

- 実装コストが比較的低い（盤面のエンジンを書かなくてよい）
- 公式テキストとQ&Aを根拠にしやすく、Evidence Gate と相性がよい
- 論点ごとに smoke テストや評価ケースを足して、回帰を確認しやすい
- 解けないケースは、保留や確信度の引き下げで逃げられる
- 処理順の原則を専用の段階に閉じ込められる

### 短所: 時系列が絡む誤答が繰り返し出る

- **時系列を1本の状態として持っていない。** Observation が浅いと、「誘発したか」と「解決するときに行動できるか」を混同しうる
- **ターンプレイヤーと非ターンプレイヤーの解決順（101.4 / 101.4a）を、決まった手順として実行していない。** LLMの観察に任せている
- **対策が「原則の文章・狭い機械判定・範囲を絞った観察」に偏っている。** 漏れがあると同じ型のミスが再発する
- **同時誘発・割り込み・置換の連鎖を、網羅的にではなく「よくある読み間違い」単位で塞いでいる**

### 実際に出た誤答（原因は同じ）

| 状況の要旨 | 誤答 | 足りないもの |
|------------|------|--------------|
| コストを払わずにクリーチャーを出す → 場にいる「バトルさせる」系のメタカードが誘発 → 出たクリーチャーの「出た時」能力でメタカードを封印 | 「封印されたので、メタカードの能力は誘発しない」 | 誘発と解決は別（110.5a）。封印で妨げられるのは、解決するときのバトル |
| 場に「山札の下に送る」系のメタカードがいる → 「出た時」に封印するクリーチャーを出す | 「山札の下に送られたので、出た時の封印は解決しない」。さらに解決順も無視 | 101.4a（ターンプレイヤーが先）と、110.5a（発生源が離れても待機は残る） |

どちらも、**知識が足りないのではなく、進行を追っていないこと**が原因。

### 対症療法の限界

`seal_pending_resolve`（`judge/validators/sealPendingResolve.ts`）のように、「バトルさせる／手札に戻す」を機械的に分ける近道を作っても、それは110.5aの一例を言い換えたにすぎない。

- デュエマの分岐は「バトルか手札か」では表せない。山札の下、破壊、入れ替え、選べない、置換、使用宣言など、いくらでもある
- パターンごとに機械判定を増やし続けるのは、実質的にルールエンジンを手で書くことで、**スケールしない**
- かといって、原則をプロンプトに書くだけではLLMが無視する（上の表のとおり）

**結論: 狭い機械判定を積み上げてデュエマ全体を扱うのは無理がある。**
master の対症療法は「わかっている地雷の応急手当」にとどめ、根本対策はステップ駆動（または、それに近い最小限のエンジン）で試す。

## 将来の実験候補: ステップ駆動（ゲーム進行のシミュレーション）

### 狙い

質問の状況を、総合ルールの進行に沿った短いタイムラインに展開する。

1. どのステップか、を決める（出す、攻撃宣言、ブレイクの前後など）
2. 誰がターンプレイヤーかを決める
3. その瞬間に誘発する能力を列挙し、待機の列に入れる
4. 101.4a に従って1件ずつ解決する。順番は、S・トリガー系 → ターンプレイヤーの待機 → 非ターンプレイヤーの待機
5. 解決のたびに、ゾーン・封印による無視・選べるかどうか、などの状態を更新する
6. 最後に、ユーザーの問いに対応する観察結果だけを回答生成に渡す

こうすると、「誘発したか」「待機は残るか」「解決するときにバトルできるか」が、**別々の出来事**として自然に分かれる。

### 想定するモジュール（案）

master の本番の流れをいきなり置き換えず、別ブランチで試作する。

```
ScenarioFacts
  → TimelineBuilder（質問 → 大まかな出来事の列。情報が足りなければ聞き返す）
  → StepEngine（状態 ＋ 待機の列 ＋ 101.4a に従う順番決め）
  → Observation（問いに対応する事実: 誘発した／解決した／不発／その理由）
  → 既存の検索 ＋ Evidence Gate ＋ 回答生成
```

- **StepEngine はできるだけ機械的に動かす。** カードごとの分岐は書かず、能力テキストのパターンやキーワードで分ける
- **LLMの役割は2つに限る。** 曖昧な質問から出来事の列を起こすことと、Observation を自然な文にすること。途中のルール適用はエンジンが行う
- **カード名での分岐は、検出・結論・プロンプトに入れない**（AGENTS.md のとおり。書いてよいのは smoke / qaSeeds / 略称辞書だけ）

### リスクと不確かな点

- 総合ルール全体を再現するのは大きすぎる（攻撃ステップ、ブレイク、置換、使用宣言、状況起因処理など）
- 質問文は盤面の情報をすべては含まない。前提が足りないときの聞き返しの設計が必須
- うまくいっても、応答時間と保守コストが増えるかもしれない
- 「出す時と同時誘発だけ」の部分的なシミュレータに絞らないと、完成しにくい

そのため、**成功するかはわからない。** 本番に入れる前に別ブランチで試作し、既存の smoke（封印×メタ、革命チェンジ後の待機、置換ブレイクなど）で比べる。

### 実験の進め方（着手するとき）

1. ブランチを切る（例: `experiment/step-engine`）
2. 範囲を「バトルゾーンに出た時の同時誘発と、101.4a による解決」だけに絞る
3. Observation を、既存の `scenarioAnalysis` に差し込み、同じ評価セットでA/B比較する
4. 正答率・保留の率・応答時間を記録し、採用／保留／却下を決める
5. 採用するときだけ [project.md](./project.md) の処理フローを更新し、master に統合する

### 成功の条件（最小）

次の2問について、カード名をハードコードせずに、Observation まで機械的に出せること。

1. 封印 × バトルさせるメタ: 能力は誘発する。ただしバトルは解決時に不発になる
2. 山札の下に送るメタ × 出た時の能力: ターンプレイヤー側の「出た時」が先に解決する（少なくとも、「発生源が離れても、出た時の待機は残る」が出せる）

これ以外は最初から対象外にする。広げたくなったら、範囲を決め直す。

### いまの扱い

- master では、論点駆動、わかっている地雷の応急手当、範囲を絞った処理順の Observation を続ける（完全な解決ではない）
- Observation を入れても時系列の誤答が残るなら、上の最小範囲で試作する価値が高い
- 完全なルールエンジンにすることや、機械判定を際限なく増やすことはしない
- このファイルは方針のメモ。試作に着手するかは、明示的に決めてから
