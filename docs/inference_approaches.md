# 裁定推論アプローチ（現状と実験候補）

裁定の正しさは「ルール知識の有無」だけでなく、**いつ・誰の効果が・どの順で・どの状態で解決されるか**の追跡に依存する。  
本書は現行パイプラインの実態と、将来試したいステップ駆動アプローチを記録する。

実装の正本フローは `docs/project.md`。ここは推論方式の設計メモ。

---

## 現状（master）: 論点駆動 + 原則制約 + LLM

ゲーム盤をシミュレートしてはいない。質問を構造化し、関係しそうな論点・原則を注入してから LLM に当てはめる。

```
質問（+ 確定カード）
  → 検索プラン（固有名・イベント・概念）
  → ScenarioFacts（主張された事実の構造化。カード属性は公式DBで上書き）
  → classifyIssues / RuleConcept（論点検出・原則・qaSeeds・ruleRefs）
  → 公式Q&A・総合ルール検索（シード強制注入）
  → 決定的 validators（解けるものは LLM なし）
  → 残余: scenarioVerifier + generateAnswer（LLM）
  → Evidence Gate（引用必須・部分一致照合）
```

### 何を「追っている」か

| 層 | 役割 | 例 |
|----|------|----|
| Facts | 質問が主張する静的事実 | マナ帯、宣言時点パワー見積もり、入れ替え阻害 |
| Issues / Concepts | 論点タグと不変条件 | `pending_abilities`, `replacement_effect` |
| Validators | 純関数で可/不可 | 多色マナ支払い、入れ替え失敗 |
| LLM 制約文 | 誤推論の禁止 | 「封印＝誘発しない」禁止、110.5a など |
| Evidence Gate | 出典の正当性 | チャンク外の捏造を拒否 |

エントリは `web/src/lib/judge/runJudge.ts`。論点レジストリは `classifyIssues.ts`、概念束は `rules/ontology/concepts.ts`。

### 長所

- 実装コストが比較的低い（盤面エンジンを書かない）
- 公式テキスト＋Q&A を根拠にしやすい（Evidence Gate と相性が良い）
- 論点ごとに smoke / eval を足して回帰しやすい
- 解けないケースは withhold / confidence で逃げられる

### 短所（今回の封印×メタで顕在化したクラス）

- **時系列を1本の状態機械として持たない**ため、「誘発したか」と「解決時に行動できるか」を混同しやすい
- ターンプレイヤー / 非ターンプレイヤーの解決順（総合ルール 101.4 / 101.4a など）を、手順として実行していない
- 対策が「原則テキストの追加」（例: `pending_abilities` の制約）に寄り、漏れが出ると同型ミスが再発する
- 同時誘発・割り込み・置換の連鎖を、網羅的にではなく「よくある誤読」単位で塞いでいる

代表例: 踏み倒し出 → メタ誘発 → 出た時で封印、のようなケース。  
正しくは「誘発はしている／バトルさせる解決は封印で不発」。現状は原則制約で矯正するが、**フロー自体が順序を保証しているわけではない**。

## 将来実験候補: ステップ駆動（ゲーム進行シミュレーション）

### 狙い

質問のシナリオを、総合ルールの進行に沿って短いタイムラインに展開する。

1. どのステップ／サブステップか（出す・攻撃宣言・ブレイク前後 など）
2. 誰がターンプレイヤーか
3. その瞬間に誘発する能力を列挙し、待機キューへ入れる
4. 101.4a に従い、S・トリガー系 → ターンプレイヤーの待機 → 非ターンプレイヤーの待機、の順で1件ずつ解決
5. 各解決の前後でゾーン・無視（封印）・選択可否などの状態を更新
6. 最後に「ユーザーの問い」に対する観測結果だけを回答生成へ渡す

こうすると、「誘発したか」「待機は残るか」「解決時にバトルできるか」が**別イベント**として自然に分かれる。

### 想定モジュール（案）

別ブランチでの試作を想定。master の本番パイプラインをいきなり置き換えない。

```
ScenarioFacts
  → TimelineBuilder（質問 → 粗いイベント列。不足は clarify）
  → StepEngine（状態 + pending queue + 101.4a スケジューラ）
  → Observation（問いに対応する事実: triggered / resolved / fizzled / reason）
  → 既存の retrieve + Evidence Gate + 回答生成
```

- StepEngine は可能な範囲で決定的にする（カード固有IFは書かない。能力テキストのパターン／キーワードで分岐）
- LLM は「曖昧な質問のイベント列起こし」と「Observation → 自然文」に限定し、途中のルール適用はエンジン側
- AGENTS.md どおり、個別カード名分岐は検出・結論・プロンプトに入れない（smoke / qaSeeds / 略称のみ）

### リスク・不確定性

- 総合ルール全体の再現は大きい（攻撃ステップ、ブレイク、置換、使用宣言、状況起因など）
- 質問文は盤面の完全情報を含まない → 前提不足時の clarify 設計が必須
- 成功してもレイテンシ・保守コストが増える可能性
- 「部分シミュレータ（出す時＋同時誘発だけ）」に絞らないと完走しにくい

そのため **成功は不確定**。本番採用前に別ブランチでスパイクし、封印×メタ／革命チェンジ後の待機／置換ブレイクなど既存 smoke で比較する。

### 実験手順（後でやるとき）

1. ブランチ例: `experiment/step-engine`（名称は任意）
2. MVP スコープを「バトルゾーンに出た時の同時誘発＋101.4a 解決」に限定
3. Observation を既存 `scenarioAnalysis` に差し込んで A/B（同じ eval セット）
4. 正答率・withhold 率・レイテンシを記録し、adopt / park / reject を決める
5. adopt 時だけ `project.md` の処理フローを更新し、master へ統合

### 現状への影響

- いまは **やらない**（ドキュメントと制約強化で凌ぐ）
- master では論点駆動を継続改善する
- 本ファイルは「後で別ブランチ実験する」ためのメモであり、実装タスクの着手宣言ではない
